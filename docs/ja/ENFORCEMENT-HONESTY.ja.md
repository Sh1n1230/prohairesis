# 強制力についての誠実さ（Enforcement Honesty）

[English](../ENFORCEMENT-HONESTY.md)

このドキュメントは、このリポジトリに強制（enforcement）のためのコードが書かれる**前**から存在しています。この順序は意図的なものです。コードを言い訳するためではなく、コードを制約するために書かれています。

もし今後の変更によってこのドキュメントの主張が偽となった場合、その変更が間違っているか、あるいは同一コミット内で弱められた保証内容を率直に明記してこのドキュメントを更新しなければなりません。

---

## 1文による保証

> **悪意（敵対的）ではなく混乱しているだけ**のエージェントに対しては、ワークスペース内のすべての影響は回復可能であり、すべての影響が記録され、何を試して何を除外したかという履歴はコンテキスト圧縮（compaction）やセッションの境界を越えて維持されます。ワークスペース外への影響は、設定されている場合はカーネルサンドボックスによって制限されます。**ここに記載されているものは、能動的に脱出を試みるエージェントに対しては何も防御しません。**

この保証こそが、権限確認（パーミッション）プロンプトをオフにすることを正当化するために必要なものです。なぜなら、現代のコーディングエージェントの失敗モードは圧倒的に「悪意」ではなく「エラー（勘違いやミス）」だからです。

これは、信頼できないリポジトリで本番シークレットを扱いながら、信頼できないエージェントを実行するために必要な保証では**ありません**。そうした用途にはコンテナやVMを使用してください。本プロジェクトは、そうでないふりをするのではなく、率直にそう述べます。

## カーネルレベルで強制されるもの

エージェントのコンプライアンス（従順さ）を入力値としないため、敵対的なエージェントであっても機能します。

| メカニズム | 実際に強制される内容 |
|---|---|
| Claude Code ネイティブサンドボックス（macOS seatbelt） | エージェントのプロセsubtreeに対するファイルシステムの読み取り/書き込みスコープ |
| `sandbox.network.strictAllowlist` | ネットワーク送信（egress）先 |
| `sandbox.credentials`（環境変数の拒否/マスク、ファイルのマスキング） | プロセス内にシークレット情報が一切実体化しないこと |
| `managed-settings.json` の所有権（`root:wheel`） | エージェントはrootとして実行されないため、ポリシーの上限そのもの |

## 勧告（アドバイザリ）に過ぎないもの

**悪意ある意図**に対してではなく、**エラーとドリフト（迷走）**に対するスピードバンプ（減速帯）です。

**L2（`PreToolUse` エバリュエーター）のすべて。** このフックはエージェント自身のランタイムによってインプロセスで呼び出され、エージェントは任意のシェルコマンドを実行できます。コマンド文字列に一致させるだけのポリシーは、最低でも以下のような方法で容易に突破されます:

```bash
X=rm; $X -rf target/            # 変数の間接参照
python - <<'PY' ... PY          # インタプリタへのヒアドキュメント
env -i sh -c '...'              # 環境のリセット
make clean                      # ビルドファイルを介した間接実行
eval "$(printf '\x72\x6d ...')" # エンコード
```

…さらに、通信が `Bash` に一切到達しないサブエージェントやMCPサーバーも存在します。

**L2を「セキュリティ」としてモデル化してはなりません。** 次の2点としてモデル化してください:

1. エージェントが通常のミスを犯すのをキャッチするコンポーネント
2. イベントログを生成するコンポーネント

このシステムから出力されるすべての決定には、`kernel` / `advisory` / `record-only` のいずれかの値を持つ `enforcement` フィールドが含まれます。このフィールドは単なるドキュメントではなく、このページの内容が単なる理想論ではなく検証可能であることを保証する構造的なコミットメントです。

シェルアクションの境界分類も同様にヒューリスティックです。シェル文字列から影響を受けるパスの集合を抽出することは一般に決定不能であり、今後もそれは変わりません。これが、**可逆性が主要なメカニズムであり、分類は二次的なメカニズムである**（決してその逆ではない）理由です。

### 証拠: 本プロジェクトが置き換えるアンチパターン

本プロジェクトが設計されたマシンでは、すでに `Bash` コマンド文字列に対する正規表現拒否リスト（denylist）フックが実行されていました。記録された74セッションにわたる実測値は以下のとおりです:

- **13個のコマンドがブロックされたが、そのうち約11個は偽陽性（誤検知）であった。**
- プロジェクトファイル群の `cat` をブロックした。理由は、ファイルの1つが `vite-env.d.ts` という名前で、`.env` ファイル向けに用意されたパターンに一致したため。
- シークレットファイルを無視することを**目的**とした `.gitignore` への追記をブロックした。
- シークレットファイルが未追跡であることを確認することを**目的**とした `git status` のチェックをブロックした。
- フック自身のソースコードを読み取ることをブロックした。
- **本ドキュメント**を作成する最初の試みをブロックした。テキストに "credentials" という単語と `.ssh` 配下のパスが含まれていたため。

一方で、さまざまなクォート形式による `cat "$HOME"/.env` は防ぐことができません。

「過剰に厳格でありながら同時に抜け穴だらけであること」は、文字列マッチングによるポリシーの**本質的な**欠陥であり、調整によって解消できる実装上の不具合ではありません。これは修正すべき対象ではなく、恒久的な回帰コーパスとしてここに保持されています。

## 検証は報告であって、ゲートではない

`prohairesis verify` は、リポジトリが既に宣言している検査を実行し、その出力を正規化するだけです。それ自体の判定は持ちません。何も拒否せず、何もブロックせず、閾値も持ちません。exit code が `1` になるのは、宣言された検査のいずれかが finding を出したときであり、それはあなたのツールの出力についての陳述であって、本プロジェクトが与えたり差し止めたりした許可ではありません。

ここから2点が導かれます。どちらも機能ではなく**限界**です。

**リポジトリの中にあるコマンドを実行します。** 発見処理は `scripts/run_quality_checks.sh`・`Makefile`・`package.json`・`Cargo.toml`・`go.mod` を読み、そこで見つけた慣習的な検査 target を、あなたの権限で、あなたの working tree で実行します。読んでいないリポジトリで `prohairesis verify` を打てば、読んでいないコードが走ります。これは *エージェント* に対しては何も新しく与えません（エージェントは既に shell を持っています）が、clone 直後のリポジトリでコマンドを打つ人間にとっては実際の考慮事項です。実行しうる target 名は閉じており（`check`・`verify`・`lint`・`typecheck`・`test`）、拡張には ADR を要するため、`deploy` target が発見されることはありません。それは影響範囲を*限定*します。*消去*はしません。そしてその手前に信頼確認が入るのは P5 からです。

**finding は近似です。** 失敗を同定する fingerprint は、タイムスタンプ・プロセスID・実行時間・一時パス・hex 識別子を消去したあとに計算されます。それらこそが、同じ失敗を新しい失敗に見せかけるものだからです。この消去は、数値だけが異なる2つの失敗を融合しえます。その上に載る count は、人間またはエージェントが**証拠として**重み付けするためのものであり、本プロジェクトのいかなる部分もそれによって自動的に行動してはなりません。

## 一切強制されないもの

- **許可リスト（allowlist）に含まれる**宛先へのデータ流出（Exfiltration）。エージェントが許可されたGitHubリポジトリにシークレットをpushすることを、ここでは何も阻止しません。
- `Bash` アクションとして現れないMCPサーバー経由で実行された操作。
- サンドボックスが確立される前に実行された操作の影響。
- 他のマシンに対する影響。
- すでにマシンの外に出てしまった影響: 送信されたメッセージ、公開されたパッケージ、実行された決済、削除されたリモートリソースなど。`prohairesis undo` はツリーを復元しますが、送信を取り消すことはできません。
- `prohairesis verify` が実行する、リポジトリ自身が宣言した検査が行うこと。その手前にサンドボックスはまだありません。

## 真の強制力はどこから得られるか

強度の昇順、および実用性の降順:

| メカニズム | 強度 | コスト | ステータス |
|---|---|---|---|
| Claude Code ネイティブサンドボックス（seatbelt） | 同一ユーザーにおいてFS + ネットワークに対して強力 | 低；一部のビルドが壊れる場合がある | 計画中 |
| 他のエージェント向けにHarnessが生成する `sandbox-exec` プロファイル | 同上、ただしプロファイルは本プロジェクトが保守 | 中；プロファイルの保守には実際の手間がかかる | 今後計画 |
| エージェント専用のUnixユーザー | 強力 — ユーザーのキーチェーン、鍵ファイル、上限設定にアクセス不可 | 高：所有権、GUI認証、開発ツールがすべて壊れる | ドキュメント化された非常用手段のみ |
| コンテナまたはVM | 利用可能な最強のもの | 最高；「自分のマシンのどのリポジトリでも動く」という前提が崩れる | **スコープ外。必要なら直接使用してください。** |

## 基本方針（The standing rule）

本システムのいかなるコンポーネントも、それがもたらすエージェンシーよりも多くのエージェンシーを損なう場合は**削除**されます。
いかなるコンポーネントも、自身が提供していない保証を理由に**保持**されることはありません。
