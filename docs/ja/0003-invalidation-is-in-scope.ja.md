# ADR 0003 —— 陳腐化した信念はスコープ内である（失われた信念だけではない）

[English](../adr/0003-invalidation-is-in-scope.md)

**Status:** accepted
**Date:** 2026-08-30
**Amends:** `docs/DESIGN.ja.md` §6.0 の L7 スコープテスト

**この決定が答えている原則:** `docs/THESIS.md` §4 の corollary —— 環境の制御は制限だけを意味しない。
「ファイルが自分の知らないうちに変わっているかもしれないと覚えておけ」と指示するのは Agent の制御で
あり、確率的で、context を食い、compaction で消える。**変更を観測可能にするのは環境の制御である。**

## Context

§6.0 は meta-state 層の境界を一つの問いで固定し、強く閉じている:

> *時刻 T に Agent が既に知っていて、時刻 T+n には失っているものは何か。*
> **その集合が L7 のスコープであり、それ以外は一切スコープ外。**

この閉包は意図的である。層が *externalization* から *augmentation* へ —— Agent が持っていたものを
戻す仕事から、持っていなかったものを供給する仕事へ —— 漂流するのを止めるために存在する。
「知っていたら有用だろう」は基準として明示的に排除されている。

その後、この問いが捉えない失敗モードが観測された。人間または第二の agent が同じディレクトリで並行して
作業していると、Agent の挙動が不審になる。**一度読み込んだファイルが変更されうるという認識が無い。**
何も失われていない。Agent は正当に獲得した信念を保持し続けており、**その信念が偽になった**のである。

設計されたままの層はこれを見られない。§6.3 は topology を「*この session* が触ったもの」に限っており、
これは**この session だけがワークスペースを乱す世界**を前提にしている。並行性は一段下では扱われている
—— `internal/session/lock.go` の repoLock は「二つの hook が競合しうる」からこそ「どの session が現在か」
の決定を守っている —— が、**ファイルについての信念の層では扱われていない。**

素直な修復（行動のたびにワークスペースを読み直す）は議論の余地なく却下する。全 tool call に掛かる
latency と context の税であり、§5 は既に L7 の能動 scan を禁じている。

## Decision

**スコープテストを、喪失に加えて陳腐化も覆う形に拡張する。**

> *時刻 T に Agent が知っていて、時刻 T+n には **失われている、または真でなくなっている** ものは何か。*

**externalization と augmentation の境界は動かない。** 陳腐化は「知っていたら有用だろう」ではない。
外部化される事実は **Agent 自身の先行する read が確立したもの**であり、harness は Agent が既に形成した
信念について判定を返すだけで、それ以上を返さない。harness がしてはならないのは、その変更が何を意味するか、
どうすべきかを述べることである —— それは戦略であり、§6.0 の非目標は一切変わっていない。

拡張を機械的に保ち、際限のない広がりを防ぐ制約が四つある:

1. **信念は ledger が read を記録した場所にのみ存在する。** `action.paths` が運用上の定義である。
   これにより拡張後のテストも元と同じ鋭さを保つ —— Agent が「本当は何を信じていたか」を議論する余地が無い。
2. **検査は既存データに対する join である。** 全 event が `checkpoint_ref` を持ち（「*checkpoint を取った
   event だけでなく、すべての event に書かれる*」）、読んだ時点の内容は既に復元可能である。コストは
   リポジトリ全体ではなく **session の read 集合に比例**する。新たに保存するものは無く、キャッシュも
   持たない: §6.3 の「腐る第二の情報源を作らない」は、ここでは特に強く効く —— **腐った情報を検出する
   機能は、腐った情報を持ち込む場所として最悪だから。**
3. **帰属は `unattributed` で止める。** 導出できるのは `変更された ∧ ¬(この session の write)` だけである。
   harness 下の別 session は区別できるが、エディタ・ビルド・人間は区別できない。event schema は
   `kind: "opaque"` について既にこの姿勢を確定している —— 一級の答えである、なぜなら対応付かない事例を
   実在のものに畳むと**網羅の錯覚を製造する**から。「人間が編集した」と書いてはならない。
4. **報告する。決してブロックしない。** lock も、陳腐化したファイルへの write の拒否も、daemon も無い。
   L5 の規則はそのまま維持される。

結果は `failure_recurrence` に並ぶ**二つ目の structured signal** として現れ、§6.2 が既に導出している
attempt 境界で発火し、事実と既存 affordance の列挙のみを運ぶ。

## Consequences

**Good.**

- 層が構造上無視してしまう失敗モードが可視になる。しかもこれは、一つのディレクトリを複数の作業者が
  共有すれば必ず踏むものである。
- 機構は P1 と P2 の出力に対する射影であり、store も watcher も新しい記録も追加しない —— これは
  §6.0 が「この層が正しく設計されていることの徴候」として挙げたもの、すなわち**推論を含まないから
  実装が小さい**、と同じ証拠である。
- **人間の決定点を増やすのではなく減らす。** 現状これは人間が「そのファイル直したから読み直して」と
  割り込むことで処理されており、`interrupts_per_session` に計上されている。friction 予算に対して
  **見出し指標を下げることで**正当化できる、数少ない機能である。

**Bad, and accepted.**

- **read 集合は完全ではない。** `truncated` は、event が単一の `write(2)` で書ける大きさを超えたため
  paths を落としたことを記録する。ゆえにこの機能は「変更を見逃さない」とは主張できず、「見逃したことは
  記録から分かる」までである。**見逃し率が signal に値するほど低いかは A1 で出荷前に測る。**
  低くなければ、これは §12 反論4 の意味での theater であり、出荷すべきではない。
- **帰属が粗い。** 「誰が」変えたのかを知りたい利用者は、ここでは答えを得られない。
- **スコープテストの適用が以前より難しくなった。** 「失われた」は鋭い問いだったが、「真でなくなった」は
  何を信念と数えるかの議論を招く。**制約1が防御のすべてであり、緩めてはならない —— ledger の read が
  無ければ信念も無い。**

## Verification

**以下はいずれもまだ存在しない。この ADR はフェーズ A1 に先行する** —— `ENFORCEMENT-HONESTY.md` が
enforcement コードに先行するのと同じ手順である。これらは A1 を閉じてよい条件である:

- 第二の書き手が read と次の attempt 境界の間にファイルを変更する scenario test: signal が発火し、
  `changed_by` が `unattributed` を超えて主張しないこと。
- `tests/golden/signal_has_no_strategy`（§13 項目4）を `stale_read` に拡張: 全フィールドが閉じた schema
  集合の内側にあり、戦略文言を含まないこと。
- signal の経路が、`tests/scenarios/p2-hook-never-blocks.sh` で hook に既に課している条件下で
  非ブロックであること。
- `truncated` による read 集合の見逃し率の実測。ADR 0002 が本プロジェクトの印字するあらゆる数字に
  要求する通り、**予算化せず記録する。**
