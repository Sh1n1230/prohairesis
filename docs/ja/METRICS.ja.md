# 各指標が支持できること、できないこと

[English](../METRICS.md)

本プロジェクトは数字で判定されることを求めている。ならばその数字は、自分が何である
かについて正直でなければならない。ここにある指標はすべて、直接は観測できないものの
**代理**である。代理を当のものとして読んだ瞬間、それは測定であることをやめて目標に
なる。そして目標を達成する最も安い方法は、行動ではなく測るものを変えることである。

本文書は `ENFORCEMENT-HONESTY.md` の対である。あちらは**実際に何が強制されているか**
を述べる。こちらは**実際に何が測られているか**を述べる。

## 2 つの規則

**測っていない値は 0 ではない。** 値を持たないものは `n/a` と理由を添えて表示する。
`false_block_rate` が 0 なのは誤って拒否されたものが無いからではない —— まだ何も拒否
していないので、誤りうる決定が存在しないから `n/a` なのである。0 と表示することは、
本プロジェクトが他のあらゆる場所で拒んでいるのと同じ種類の嘘を、文章ではなく数字で
つくことになる。

**比較の両側は同じコードから出す。** install 前の baseline と現在の値は、同じ関数が
同じ入力を時間で分割して計算する。片方を bash で、もう片方を Go で計算したものは比較
ではない。2 つの実装の差は、測ろうとしている効果と区別がつかない。

## 数字の出所

出所は 2 つあり、どちらか一方だけでは足りない。

**runtime の transcript**（`~/.claude/projects/**.jsonl`）は、**人間**が見える唯一の
場所である。本プロジェクトが入れる hook は tool call を見るが、キーボードを打っている
人間は見ない。介入回数と無停止区間の長さは、そこからしか読めない。

**event log**（`~/.prohairesis/sessions/<id>/events.jsonl`）は、本プロジェクト自身の
振る舞いが見える唯一の場所である。何を記録し、何を checkpoint し、何を失い、hook が
どれだけ時間を使ったか。

「以前」と「以後」の境界は **event log 自身から導出する** —— 記録された最も古い event
が、定義上、本プロジェクトが見始めた瞬間である。どこにも保存しない。install 日時を
記録すればそれはこの事実の第二の複製になり、いつでも食い違える。

## カバレッジを毎回表示する理由

hook は 1 つの repository にも machine 全体にも登録できる。project scope では他の
repository での作業は不可視になる —— そして 10 個中 1 個だけを黙ってカバーする event
log は、log が無いより悪い。その沈黙が証拠に見えるからである。

だから `metrics` は自分の数字がどの repository をカバーしているかを表示し、`doctor` は
どの scope が記録中かを報告する。カバレッジを欠いた数字は「小さめの真実」ではない。
**別の主張**である。

穴についても同じ。観測が書けなかったとき、その事実は専用の durable な経路
（`~/.prohairesis/telemetry-loss.jsonl`）に記録され、`doctor` と `metrics` の両方が件数
を表示する。連番の欠落は log を読むときに数える。印の無い穴を持つ log は、不在を静けさ
として読ませてしまう。

## 指標

### 今測れるもの

| 指標 | 何を数えているか | 方向 | これでは分からないこと |
|---|---|---|---|
| `interrupts_per_session` | 人間のターン + 明示的な tool 拒否 | ↓ | **なぜ**人間が介入したか。興味から発した質問も、ブロックされて強いられた介入も同じ 1 になる |
| `mean_uninterrupted_run` | 連続する人間ターン間の実時間 | ↑ | 人間が離席した session について何も。それが値を大きく膨らませる。中央値を読むこと |
| `median_uninterrupted_run` | 同上、中央値 | ↑ | 分布の形。二峰性はここに隠れる |
| `tool_calls_per_human_turn` | 総数の比 | ↑ | その増えた呼び出しが有用だったか。1 ターンあたりの呼び出しが増えることは、進捗が増えることではない |
| `recurrence_rate` | 同一 session 内で既出の正規化 fingerprint を持つ失敗の割合 | ↓ | 言い回しの違う 2 つの失敗が本当に同じ失敗だったか。fingerprint は機械的（小文字化・path/hex/数値の除去）で解釈を一切含まない。それが「静かに判断になる」ことを防いでいる |

### 記録するが、予算にはしないもの

`hook time` の p50 と p99 は表示するが、何とも比較しない。

設計文書は受け入れ条件を「p50 < 20ms」としていた。この数字はどこからも導出されていな
かった —— 1 回だけ現れ、別の議論のために使われた見積もりに紐付いていた。それを根拠の
無い第二の数字で置き換えるのではなく、P2 は分布を記録して待つ。実 session が十分溜まれ
ばそこから閾値を導出できる。friction について P0 が踏んだのと同じ順序であり、比較対象の
baseline が存在するのはそのおかげである。
[ADR 0002](0002-what-the-event-log-keeps.ja.md) を参照。

この数字を引用する前に知っておくべきことが 2 つある:

- **hook 自身の数字は過小である。** event log の `hook_ms` はプロセス内部で測っており、
  自分を起動した exec を計測できない。プロセス起動はコストの大部分を占める。
  `tools/hook-latency.py` は呼び出し全体を外側から測る。意味を持つのはこちらである。
- **checkpoint を取る呼び出しは高く、別に測る。** 自動 checkpoint は設計上同期実行で
  ある —— checkpoint より先に着地した effect は、本プロジェクトが与える唯一の保証の外
  にある —— したがってそのコストは平均に溶かさず単独で示す。

このマシン（macOS, APFS）での実測: 記録のみ p50 23ms・p99 27ms、checkpoint を伴う場合
p50 58ms・p99 62ms。

### 定義済みだが、まだ測れないもの

これらは省略せず `metrics` が列挙する。埋まる phase まで静かに消えている指標は、欠けて
いることに誰も気づかない指標であり、測る対象は「たまたま簡単なもの」へ流れていく。

| 指標 | 何を待っているか |
|---|---|
| `false_block_rate` | P5。まだ何も拒否しないので、誤りうる決定が存在しない |
| `context_tax` | P4。いまは注入している —— session 開始時の 1 行のみで、それを書くコード自身が 200 バイト上限を強制しており、実測 162 バイト。したがって分子は正確に判っている。分母が無い。このプログラムから session の token 数は見えず、推定値で割れば誤差を誰も評価できない比になる |
| `resignation_rate` | P4b。verification contract は実装されたので「green に到達したか」は答えられる。もう半分が無い —— 諦めと結論を分けるのは、理由と根拠を伴う棄却であり、それは declared state である |
| `strategy_revision_rate` | P4。存在しない層の効果を測る指標である |
| `rediscovery_cost` | P4。再探索を知るには、既に探索済みの記録が要る |

`resignation_rate` には、実装された後も残る警告を先に書いておく: これは諦念の**近似**
であり、単独では、諦めた session と正しく不可能と結論した session と人間が途中で終えた
session を区別できない。単独では決して読まないこと。DESIGN §9.1 を参照。

## プロジェクトの将来を決める唯一の指標

`mean_uninterrupted_run` は、phase 順序の背後にある作業仮説 —— autonomy はおよそ
agency × verification × persistent state × recovery である —— の検定である。P4 完了
時点でこれが動いていなければ仮説は誤りであり、正直な対応は、優しい指標を探すことでは
なく、本プロジェクトを可逆性層と監査層に縮退させることである。

それを、事前に、意図してここに書いておく。

## baseline と、その実装を置き換えた移植

`~/.prohairesis/metrics/baseline.json` は `tools/baseline.sh`（bash と jq）が、本
プロジェクトがこのマシンに何かを変える前に取得したものである —— 意図的に。baseline が
測定対象の影響を受けないようにするためである。

`prohairesis metrics` はその数字を読まない。同じ transcript から Go で両側を再計算する。
2 つの実装をまたぐ比較は、効果と同じくらい実装を測ってしまうからである。bash 版は P0 の
成果物として、また独立実装による照合手段として残す。

同一コーパスに対し同時刻に走らせた結果、両者は一致する:

| 指標 | `tools/baseline.sh` | `prohairesis metrics` |
|---|---|---|
| sessions | 74 | 74 |
| `interrupts_per_session` | 7.9865 | 7.99 |
| `mean_uninterrupted_run` | 2756.4 s | 2.76e+03 s |
| `median_uninterrupted_run` | 291 s | 290 s |
| `tool_calls_per_human_turn` | 13.7718 | 13.8 |
| `recurrence_rate` | 0.1445 | 0.144 |

中央値が 1 秒違うのは、gap 列の要素数が 1 つ異なることと整合する。表示精度において他に
差は無い。

なお、これらの数値は commit されている `baseline.json` のものとは異なる。あちらは 9 時間
前に取得されたもので、作業を続けるあいだコーパスは増え続けるため、再実行しても古い
スナップショットは再現しない。これは測定の性質であって、どちらの実装の欠陥でもない。
上の比較を両者同時に走らせたのはそのためである。
